# Refactor: Split Entity Modals (Create/Edit) from Assignment Modals + New Students Tab

## Current State (verified)

The active admin UI is the vanilla-JS app in the repo root (`admin.html` + `category-management.js`, `exam-management.js`, `class-management.js`, `styles.css`) — NOT `src/frontend` (that's the newer but unused SPA; nothing there is wired into `admin.html`).

Today, one giant modal per entity mixes everything:
- **Category modal** (`admin.html:3223`–3465, driven by `category-management.js:282-553`): name/description/color fields **plus** the full "Assign Questions" section (filters, quick-filters, Available/Selected columns, points badge).
- **Exam modal** (`admin.html:5239`–5470, `exam-management.js:72-165, 1586-1765`): name/duration/preset fields **plus** the whole question picker (filters + Available/Selected columns).
- **Class modal** (`admin.html:5473`–5653, `class-management.js:53-127, 570-786`): class name **plus** student roster management (add student, user picker, import/export CSV) **plus** exam assignment list.

Persistence flows through `window.API` (server-first) with a localStorage mirror via `window.__DI_CONTAINER__.repo`, plus `window.Auth.syncClassStudentsFromClassData()` for rosters.

## Target Ergonomy (Molish design)

**1. Create/Edit modals = lean entity forms only**

| Modal | Fields kept | Sections removed |
|---|---|---|
| Category | Name, Description, Color picker | Assign Questions section (moved to new Assign modal) |
| Exam | Name, Duration, Settings Preset (+ passing score if present) | Select Questions section (moved) |
| Class | Name only | Students roster + Assign Exams (moved) |

**2. New "Assign" action button in each table's actions cell** (Categories, Exams, Classes tables — `.exam-actions` row buttons), purple gradient style consistent with existing `.exam-view-btn` family:
- Categories table: **Assign Questions** → opens Assign Questions modal for that category
- Exams table: **Assign Questions** + **Assign Classes** → two assign modals
- Classes table: **Assign Students** + **Assign Exams** → two assign modals

**3. New dedicated Assign modals** (moved, not rewritten — the question picker columns/filters move as a unit):
- `assignCategoryQuestionsModal` — the existing category-filter-section + question-selection-container markup moves here, headed by the category name. Save applies question→category assignment (same logic as today's `saveCategoryForm` question part).
- `assignExamQuestionsModal` — exam-filters-container + question columns move here. Save applies `exam.questions` (today's save logic, split out).
- `assignExamClassesModal` — compact checklist of classes (checkbox list styled like `admin-checklist` pattern) → updates `exam.classes` both sides.
- `assignClassStudentsModal` — the existing roster UI (number/name entry, user picker, import/export CSV buttons, selected list) moves here.
- `assignClassExamsModal` — the existing exam selection list (`#availableExams` + search) moves here.

All assign modals keep the unified `modal-header-with-icon` + icon color design (icon-amber for category-assign, icon-green for exam-assign, icon-blue for class-assign), `small-modal`→`modal-content` sizing consistent with peers, staging behavior with a **Save/Apply** footer (matching today's UX where selections are staged then saved), and get promoted to body with the same `promoteClassModal`-style overlay fix so stacking works.

**4. New "Students" top-level tab** between Classes and Results:
- Nav button (`data-tab="students"`, `data-roles="admin,teacher"`, users icon) + `<section id="students">` with the standard toolbar pattern (h2 "Student Management", Add Student button, search, filter by class, sort) + `table-container` with columns: Number, Name, Class, Status, Exams? , Actions (Edit, Assign to Class, Delete).
- Data source: student users via `window.Auth.getUsers()` (role === 'student'), the same store the class roster syncs to.
- Toolbar Import/Export CSV reuses the existing `exportStudents`/`importStudents` CSV logic, retargeted to work on the whole student body instead of one class's roster.
- Add/Edit student modal: lean form (number, name, class select) that creates/updates student users via `Auth` (default password flow like `syncClassStudentsFromClassData`).
- **Teacher-access wiring**: add `students: true` to `DEFAULT_TEACHER_ACCESS.tabs` (auth.js:548), `DEFAULT_SETTINGS.teacherAccess.tabs` (settings.js:27), the `tabMap`s in `populateTeacherAccessForm`/`readTeacherAccessForm` (settings.js:453, 501), and a "Students" switch (`teacher-access-students`) in admin.html's teacher-access grid — so the tab is controllable like the others.

**5. Row actions after refactor** (each table keeps Edit/Delete plus new Assign):
- Categories: Edit | Assign Questions | Delete (system categories: only Assign)
- Exams: Edit | Assign Questions | Assign Classes | Push | Stop | Delete
- Classes: Edit | Assign Students | Assign Exams | Delete

## Key Implementation Details

- **Move, don't rewrite**: the question picker columns, filters, quick-filters and their JS (`loadAvailableQuestionsForCategory`, `filterExamQuestionsEnhanced`, `toggleQuestionSelection...`, user picker, CSV import/export) already work against element IDs — those IDs stay identical, the containers just live in new modal markup. Only the opener/save functions change.
- **Stacking/promotion**: new modals get the same `promoteXModal` body-promotion treatment (copy `promoteClassModal` pattern) so they render above everything.
- **Save behavior in assign modals**: staged selections + one Save button that performs the same persist sequence as today (API first, then localStorage mirror, then table refresh + dashboard refresh). Cancel discards without persisting.
- **Students tab access**: `canAccessTab('students')` works automatically once the nav button has `data-roles` — no auth.js logic change beyond the DEFAULT_TEACHER_ACCESS entry.
- **Back-compat**: `window.saveCategory`, `window.editClass` etc. stays; e2e `scripts/e2e-lobby-test.mjs` doesn't touch these modals (verified), so no test churn.
